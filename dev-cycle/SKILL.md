# Цикл разработки

Режим для работы, где предметная область сложнее кода: новая подсистема,
внешний продукт, интеграция с чужой моделью, разбор монолита на сервисы.
Не для однострочных правок и не для разведки — там дешевле просто сделать.

Отличие от режима плана: план живёт в контексте и исчезает после
`/compact`. Модель живёт в репозитории, её можно закоммитить, отревьюить
и открыть через полгода, чтобы понять, почему код такой.

Главная ценность режима — **не документы, а трассировка**. Каждый элемент
модели знает, из какой пользовательской истории он взялся. Элемент, который
этого не знает, — либо забытая история, либо расползание рамок.

Навык разложен по файлам, чтобы в контексте было только нужное сейчас:
здесь — правила любого шага; как делать конкретный шаг — в `steps/`;
редкие процедуры — в `references/`; всё механическое (номера, ссылки,
покрытие) считает `scripts/trace.py`.

## Аргументы

| вызов | что делать |
|---|---|
| `/dev-cycle` | показать статус шагов и продолжить с первого неутверждённого |
| `/dev-cycle status` | показать текущую модель и её состояние, ничего не менять |
| `/dev-cycle use <модель>` | переключиться на другую модель в этом же дереве |
| `/dev-cycle stories <файлы или описание>` | шаг 1: черновик историй из сырого материала |
| `/dev-cycle <N>` | выполнить шаг N (даже если предыдущие не утверждены — предупредить) |
| `/dev-cycle slice <slug>` | шаги 9–10 по выбранному куску модели |
| `/dev-cycle accept <slug>` | шаг 12: приёмка среза, у которого сделаны все задачи |
| `/dev-cycle change <описание>` | провести новое требование, правку или отмену через готовую модель — `references/answer-and-change.md` |
| `/dev-cycle answer Q-N ⟨ответ⟩` | внести новую информацию или выбор по развилке и пересмотреть всё, что на ней держалось — `references/answer-and-change.md` |
| `/dev-cycle spec [strs\|syrs\|srs <slug>]` | собрать спецификации из модели — `references/specs.md` |
| `/dev-cycle check` | только проверка трассировки и покрытия, без правок |

Ответ на развилку можно дать и коротко — «Q-4: B», «по Q-4 второй
вариант»: это тот же `answer`.

Любой вызов можно дополнить моделью прямо в тексте — «`/dev-cycle 2`
в merchant-screening». Названная в вызове модель имеет приоритет над
запомненной и **запоминается** так же, как после `use`.

## Какая модель сейчас

В одном рабочем дереве моделей может быть несколько: `merchant-billing/`,
`merchant-screening/` — каждая со своим `docs/model/`. Тогда «текущую»
надо знать явно, иначе правки уедут не в ту модель, и заметит это никто
не сразу: файлы называются одинаково, номера `USRSTR-1` есть в обеих.

**Текущая модель хранится в файле `.dev-cycle` в корне рабочего дерева.**
Одна строка — путь к корню модели относительно этого корня:

```
merchant-billing/docs/model
```

Как она определяется, по порядку:

1. Модель названа в самом вызове — берётся она, файл `.dev-cycle`
   перезаписывается.
2. Файл `.dev-cycle` есть и путь существует — берётся оттуда.
3. Файла нет: найти в дереве все `*/docs/model/` и `docs/model/`.
   Нашлась ровно одна — взять её и записать в `.dev-cycle`, сказав об этом
   одной строкой. Нашлось несколько — **остановиться и спросить**, какую,
   перечислив найденные. Не выбирать по времени изменения и не угадывать
   по контексту разговора.

Файл `.dev-cycle` — личное состояние разработчика, а не часть модели.
Стоит добавить его в `.gitignore`; сам этого не делай, скажи человеку.

### `/dev-cycle use <модель>`

Принимает и имя папки (`merchant-screening`), и путь к корню модели
(`merchant-screening/docs/model`). Проверить, что `docs/model/` там
действительно есть; если нет — сказать и не переключаться, а не создавать
пустую модель молча.

После переключения показать то же, что `status`, — иначе непонятно,
куда попал.

### `/dev-cycle status`

Ничего не меняет. Показать:

- **корень текущей модели** — полным путём, чтобы не было сомнений;
- таблицу шагов из `INDEX.md` с их статусами и первый неутверждённый;
- сколько открытых вопросов и живых предположений;
- сколько рисков заведено и сколько без обработки;
- **другие модели, найденные в дереве**, — одной строкой, чтобы было
  видно, куда можно переключиться.

Если текущая модель не определена — сказать об этом прямо и перечислить
найденные, а не молчать.

Всё это выдаёт `trace.py status` — покажи его вывод, а не собирай руками.

## Где живут файлы

Корень модели — `docs/model/` в проекте (не в `~/.Codex`: модель
принадлежит проекту). Если в проекте уже есть свой корень документации,
используй его и скажи об этом. Когда моделей в дереве несколько — см.
раздел выше.

```
docs/model/
  INDEX.md                          сводная таблица, вопросы, обратный индекс
  risks.md                          реестр рисков (сквозной, любой шаг)
  user-stories/USRSTR-1-<slug>.md   шаги 1–2
  nfr.md                            нефункциональные требования (шаг 2 и позже)
  roles-and-aggregates.md           шаг 3
  relations.md                      шаг 4
  processes/PROC-1-<slug>.md        шаг 5
  states-and-attributes.md          шаг 6
  lifecycles/AGGR-1-<slug>.md       шаг 7
  metrics.md                        шаг 8
  slices/<slug>/design.md           шаг 9
  slices/<slug>/tasks.md            шаг 10
  slices/<slug>/acceptance.md       шаг 12
  specs/StRS.md, SyRS.md            сборка из модели
  specs/SRS-<slug>.md               сборка по срезу
```

Сам навык:

```
dev-cycle/
  SKILL.md           правила любого шага — этот файл
  steps/NN-*.md      как делать шаг N; читать перед шагом
  references/        риски, ответы и изменения, соседние модели,
                     спецификации, ручная проверка покрытия
  scripts/trace.py   номера, ссылки, покрытие, влияние изменений
  templates/         скелеты документов
  examples/          эталонная модель, если положена
```

Шаблоны — в `templates/` рядом с этим файлом. Шаблон это скелет, а не
форма для заполнения: не копируй подсказки в скобках в итоговый документ.

Язык документов — язык проекта: посмотри соседние `*.md` и AGENTS.md.

## Трек-номера

Где у элемента ровно один родитель — номер вложенный, и трассировка
видна из самого номера. Где родителей может быть много — номер сквозной,
а связи пишутся отдельной строкой `← ...`.

| элемент | номер | шаг |
|---|---|---|
| пользовательская история | `USRSTR-N` | 1 |
| критерий приёмки | `USRSTR-N/ACPT-M` | 2 |
| нефункциональное требование | `NFR-N` ← истории, риски | 2, может всплыть позже |
| роль | `ROLE-N` ← истории | 3 |
| агрегат (сущность) | `AGGR-N` ← истории | 3 |
| связь | `REL-N` ← роли, агрегаты, истории | 4 |
| процесс | `PROC-N` ← истории, роли, агрегаты | 5 |
| состояние | `AGGR-N/ST-M` | 6 |
| атрибут | `AGGR-N/ATTR-M` ← критерии, процессы | 6 |
| переход жизненного цикла | `AGGR-N/TR-M` ← процессы, критерии | 7 |
| метрика | `MTR-N` ← истории, переходы, атрибуты | 8 |
| проектное решение | `DES-N` ← всё, что выше | 9 |
| задача | `TASK-N` → критерии, НФТ | 10 |
| риск | `RISK-N` ⚠ затрагивает элементы | любой |
| вопрос | `Q-N` | любой |

Номера уникальны **в пределах одной модели**. О ссылках в соседние модели —
раздел ниже.

Три правила, без которых схема бесполезна:

1. **Номер не меняется никогда.** Переименовали элемент — номер остался.
   Иначе все ссылки в шести документах превращаются в мусор.
2. **Номер не переиспользуется.** Удалили `USRSTR-4` — четвёрка больше
   не выдаётся. В `INDEX.md` строка остаётся с пометкой «удалено <дата>».
   Сам элемент из файла не стирается, а помечается строкой
   «Удалено ⟨дата⟩: ⟨причина⟩» — по ней строка в `INDEX.md` и сохраняется.
3. **Ссылка `←` ведёт только вверх по таблице.** Процесс ссылается на
   истории и агрегаты; агрегат на процесс — никогда. Ссылка вниз означает,
   что шаги перепутаны местами. Элементы одного шага друг на друга тоже
   не ссылаются: роль — на агрегат, НФТ — на критерий. Риск и вопрос стоят
   вне цепочки.

**Номер выдаёт скрипт** — `trace.py next-id`, непосредственно перед записью
элемента в файл. Счёт «на глаз» по открытым файлам ошибается ровно тогда,
когда это дороже всего: при удалённых номерах и нескольких моделях.

## Формат документов

Скрипт читает модель по нескольким соглашениям. Шаблоны в `templates/`
им следуют; если скрипт чего-то не распознал, сначала проверь формат,
а уже потом модель.

- **Где определён элемент.** У каждого вида номера свой файл (дерево
  выше): роли и агрегаты — в `roles-and-aggregates.md`, переходы —
  в `lifecycles/` и так далее. Тот же номер в другом файле — упоминание.
- **Как определён.** Заголовок, начинающийся с номера (`### ROLE-2. Менеджер`);
  строка таблицы с номером в первой ячейке; пункт списка, начинающийся
  с номера и точки или двоеточия (`- [ ] TASK-3. Название`). История —
  ещё и именем файла `USRSTR-N-<slug>.md`.
- **Повтор номера** в другом разделе того же файла — сводки вроде
  «Догадки» или «Чего не хватает в модели» — упоминание, а не второе
  определение.
- **Ссылки вверх** — строка с `←` в разделе элемента (`**← истории:** USRSTR-1`);
  у задач — строка, начинающаяся с `→`. В таблице — столбец с `←`
  в заголовке или ячейка, начинающаяся с `←`.
- **Риск** — `**⚠ затрагивает:**` с номерами, `**Обработка:**` — один
  из четырёх способов, `**Чем закрыт:**` — номер критерия, НФТ или
  решения, документ или причина.
- **Предположение** — `‼ **Предположение** (Q-N): …` в разделе элемента;
  у строки таблицы — в её ячейке: `‼ (Q-N): …`.
- **Удаление элемента.** Элемент с заголовком — строка
  `Удалено ⟨дата⟩: ⟨причина⟩` или `Отменено ⟨дата⟩: ⟨причина⟩` сразу под
  заголовком; такая же строка ниже по тексту относится к прежней
  формулировке, а не к элементу. Элемент из таблицы — строкой в таблице
  «Удалённые элементы» своего файла, с датой; риск — в «Снятых».
  Отклонённый кандидат в агрегаты — «отклонён» в столбце «статус».
- **INDEX.md** — две таблицы собирает скрипт: статус шагов (между
  `<!-- trace:steps:begin -->` и `<!-- trace:steps:end -->`) и реестр номеров
  (между `<!-- trace:begin -->` и `<!-- trace:end -->`). Вопрос — строка
  в «Открытых вопросах», отвеченный — статус «закрыт ⟨дата⟩» и строка
  в «Полученных ответах». Обратный индекс — таблица `| Q-N | номера |`.
- **Срез** — в `design.md` строка `**Состав среза:** USRSTR-3, USRSTR-5/ACPT-2, NFR-1`.
- **Тест** — комментарий `verifies: USRSTR-3/ACPT-2` у теста, на любом языке.
- **Внешняя ссылка** — префикс вплотную к номеру: `merchant-screening:USRSTR-7`.
- Номера внутри блоков кода (mermaid) ссылками не считаются.

## scripts/trace.py

Всё механическое — номера, ссылки, покрытие — делает скрипт, а не чтение
всех файлов подряд: так быстрее, дешевле и без ошибок в счёте. Тебе
остаётся то, что скрипт проверить не может, — смысл.

```
python3 <папка навыка>/scripts/trace.py check                  # перед каждым остановом
python3 <папка навыка>/scripts/trace.py next-id AGGR-2/TR      # перед записью элемента
python3 <папка навыка>/scripts/trace.py next-id USRSTR -n 5    # несколько номеров сразу
python3 <папка навыка>/scripts/trace.py impact USRSTR-4 Q-3    # что держится на номерах
python3 <папка навыка>/scripts/trace.py index --write          # сводная таблица INDEX.md
python3 <папка навыка>/scripts/trace.py tests --slice <slug>   # покрытие проверками, шаг 12
python3 <папка навыка>/scripts/trace.py status                 # для /dev-cycle status
```

Запускай из корня рабочего дерева: модель скрипт определяет по тем же
правилам, что и ты, а `--model` задаёт её явно.

- Номер — только от `next-id`, сразу перед записью. Два вызова подряд
  без записи дадут один и тот же номер; для нескольких элементов — `-n`.
- `check` — до каждого останова. Ошибку, которая твоя недоделка (забыл
  `←`, не записал в обратный индекс), исправь. Расхождение в материале
  покажи как находку. Молча не чини то, что меняет смысл.
- `index --write` — после каждого шага, чтобы `INDEX.md` не отставал.
- Результат проверки в файлы не пишется: записанный, он устаревает
  с первой правкой. Его место — останов.
- Скрипт не меняет модель, кроме блока сводной таблицы.
- Нет `python3` — проверь вручную по `references/coverage.md` и скажи
  об этом на останове.

## Ссылки между моделями

Нумерация локальна для модели: `USRSTR-1` есть в каждой. Ссылка наружу
обязана нести префикс модели — имя репозитория или папки проекта, как
оно есть на диске: `merchant-screening:USRSTR-7`,
`merchant-screening:USRSTR-7/ACPT-3`. Без префикса ссылка всегда читается
как внутренняя.

Ссылка наружу — зависимость, о которой соседняя модель должна знать.
Прежде чем поставить внешнюю ссылку или поменять элемент, на который
ссылаются снаружи, прочитай `references/cross-model.md`.

## Предположения и их пересмотр

Работа почти никогда не начинается с полными ответами. Ждать их — значит
не начать; молча выбрать одну версию — значит потом не найти, где выбор
был сделан. Поэтому элемент, который держится на неподтверждённом
допущении, помечается прямо в своём файле:

```
‼ Предположение (Q-3): перечень наблюдаемых лиц хранится на нашей стороне.
  При ответе «у Мерчанта» история меняется целиком.
```

Пометка обязана называть **вопрос**, от которого зависит, и **что именно
допущено**. «Требует уточнения» без номера вопроса — не пометка: такое
не найти автоматически, когда ответ придёт.

В `INDEX.md` ведётся **обратный индекс**: вопрос → элементы, которые
придётся пересмотреть. Он заполняется в момент появления предположения,
а не в момент получения ответа.

| Q | Что пересмотреть при ответе |
|---|---|
| Q-3 | USRSTR-4, USRSTR-4/ACPT-1, USRSTR-4/ACPT-3, RISK-8 |

Когда приходит ответ — `/dev-cycle answer` — процедура в
`references/answer-and-change.md`. Развилка на останове (ниже) — тот же
механизм: вопрос с вариантами и черновик по рекомендованному варианту
с пометкой `‼`.

## Риски

Риск — то, что может обесценить работу сервиса, но не является ничьей
потребностью: недоступность внешнего источника, правовое ограничение,
молчаливая деградация вместо явного отказа. Историей его не делают,
а терять нельзя.

Риск заводится **на любом шаге**, как только всплыл: `RISK-N` в `risks.md`,
с источником `←`, затронутыми элементами `⚠` и обработкой — одним из
четырёх способов: критерием, решением, вне модели, принят. «Принят» — это
решение, а не его отсутствие. Риск, закрытый критерием или решением,
упоминается в самом критерии или решении. Перед тем как завести первый
риск в этой сессии, прочитай `references/risks.md`.

## Шаги

Главное в этом режиме — **остановки**. После каждого шага ты пишешь
файлы, показываешь суть в 3–5 строках, показываешь результат проверки
покрытия и ждёшь ответа. Не переходишь к следующему шагу сам.
Не пишешь код на шагах 1–10. Если на шаге всплыл риск — заводи `RISK-N`
сразу и показывай новые риски на том же останове.

Перед любым шагом прочитай, что уже есть: существующие документы модели,
код по теме, AGENTS.md. Модель, написанная без чтения кода, врёт в деталях.

| шаг | что | инструкция |

чем по описанию.

## Останов

Останов — единственное место, где человек видит работу, поэтому у него
постоянная форма:

```
Шаг N. <название> — черновик. Файлы: <что записано или изменено>

<суть в 3–5 строках>

Проверка: <ошибки и «проверить» из trace.py check; если чисто — одной строкой>
Новые риски: <RISK-N одной строкой каждый, если есть>

Проверьте глазами:
  <3–5 конкретных вопросов по чеклисту шага>

Нужно ваше решение:
  <развилки Q-N с вариантами и рекомендацией>
  или: «Развилок нет. Утвердите шаг или скажите, что поправить.»
```

Дальше ждёшь ответа. К следующему шагу сам не переходишь, даже если
развилок нет.

### Проверьте глазами

В файле каждого шага есть чеклист — вопросы смысла, которые скрипт
проверить не может. Пройди его сам до останова: что нашёл — это находка,
покажи её в проверке. Человеку покажи чеклист **конкретными вопросами
по этой модели**: не «нет ли двух названий одной роли», а «ROLE-2
„Менеджер“ и ROLE-4 „Руководитель отдела“ — не одна ли это роль?».
Пункт, по которому в этой модели смотреть нечего, пропусти. Общий вопрос
человек без опыта в аналитике пропустит, конкретный — проверит.

### Развилки

Останов, который только сообщает, что сделано, оставляет человеку самое
трудное — заметить, где был выбор. Поэтому он заканчивается блоком
«Нужно ваше решение».

Развилка — место, где материал допускает два прочтения или модель можно
построить двумя способами, **и ответ меняет следующие шаги**. Если ниже
от ответа ничего не зависит, это не развилка, а строка в «Открытых
вопросах».

Каждая развилка:

- заводится как вопрос `Q-N` (номер — `next-id Q`);
- даёт 2–3 варианта, и у каждого — последствия в номерах и шагах: что
  появится, исчезнет, изменится;
- заканчивается рекомендацией с причиной из материала, а не из общих
  соображений;
- черновик пишется по рекомендованному варианту с пометкой
  `‼ Предположение (Q-N)` и строкой в обратном индексе. Так работа
  не стоит, а выбор не теряется.

```
Q-4. «Менеджер» (USRSTR-2) и «руководитель отдела» (USRSTR-5)
  A. Одна роль ROLE-2 с разными правами — связи проще, права уйдут в атрибуты
  B. Две роли ROLE-2 и ROLE-3 — на шаге 4 появится REL-N, на шаге 5 процессы разойдутся
  Рекомендую A: в материале нет действий, доступных только руководителю.
  Черновик написан по A, помечено ‼ (Q-4).
```

Не больше трёх развилок за останов. Если их больше, покажи три, от которых
зависит больше всего, остальные оставь в «Открытых вопросах» и скажи,
сколько их.

Если в среде есть инструмент вопросов с вариантами (в Codex —
AskUserQuestion), задай развилки через него: один вопрос — одна развилка,
вариант — короткая метка, последствия — в описании варианта, рекомендованный
вариант первым с пометкой «рекомендую». Сводку и проверку всё равно покажи
текстом до вопросов. Выбор человека — это `answer Q-N`.

Рекомендация — не решение. Снять `‼` можно только по ответу человека.

## Статус шага

Первая строка каждого файла:

```
> Статус: черновик
```

После утверждения человеком заменить на:

```
> Статус: утверждено 2026-08-31
```

Дату брать из окружения, не выдумывать. По этой строке `/dev-cycle` без
аргументов определяет, где продолжать.

## Когда модель расходится с реальностью

Это происходит почти всегда: на шаге 9 выясняется, что модель чего-то не
учла. Правило одно — **правится документ, а не только код**. Внеси
изменение в нужный документ, отметь строкой «Изменено ⟨дата⟩: ⟨что и
почему⟩» и скажи человеку. Модель, которая разошлась с кодом и молчит об
этом, хуже отсутствия модели.

Если правка на верхнем шаге меняет то, что ниже — **не перегенерируй
нижние документы молча**. Покажи список затронутых номеров — его даёт
`trace.py impact` — и спроси.

Если расхождение отменяет принятое решение — не стирай прежнее, оформи
как запись об отмене с датой и причиной.

## Чего не делать

- Не писать код на шагах 1–10, даже «для примера».
- Не проходить два шага за один ответ, даже если задача кажется мелкой.
  Мелкой задаче не нужен этот режим — скажи об этом и предложи без него.
- Не выполнять шаг, не прочитав его файл в `steps/`.
- Не изобретать истории, роли и атрибуты, которых нет в материале. Всё
  недостающее — в «Открытые вопросы», а не в модель.
- Не менять и не переиспользовать трек-номера и не выдавать номер мимо
  `next-id`.
- Не править модель, не убедившись, какая из них текущая: при нескольких
  моделях в дереве спросить, а не выбрать за человека.
- Не ссылаться на чужую модель без префикса — такая ссылка читается как
  внутренняя и однажды укажет не туда.
- Не ставить внешнюю ссылку, не записав её в разделе «На нас ссылаются»
  соседней модели.
- Не сглаживать противоречия в исходном материале, чтобы модель выглядела
  цельной. Противоречие — это находка, а не дефект документа.
- Не растворять риск в тексте документа абзацем «стоит иметь в виду».
  Не попавший в `risks.md` риск не имеет ни номера, ни обработки, ни
  того, кто о нём вспомнит.
- Не выбирать молча одну из двух версий, когда вопрос открыт. Выбрать
  можно — но как развилку: с пометкой `‼` и строкой в обратном индексе.
- Не снимать `‼` по собственной рекомендации — только по ответу человека.
- Не править по ответу на вопрос молча, даже когда правка очевидна.
  Сначала показать весь список затронутого.
- Не начинать шаг 9, пока шаги 1–8 не утверждены. Проектирование по
  неутверждённой модели — самый дорогой способ ошибиться.
- Не показывать человеку общий чеклист там, где можно задать конкретный
  вопрос по модели.
- Не вести StRS, SyRS и SRS руками и не править их на месте — подробности
  в `references/specs.md`.
