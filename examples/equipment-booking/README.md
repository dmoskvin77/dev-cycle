# Как меняется правило бронирования

Этот вымышленный пример охватывает один слот для одной камеры. Снимок модели показывает результат согласования между сотрудником и администратором. В коде последовательные вызовы, хранение в памяти и имитация роли вызывающей стороны.

1. Начните с [заметок встречи](meeting.md). Сотрудник хочет сразу видеть, что камера за ним. Администратор хочет сначала проверить расписание.
2. Сопоставьте [историю сотрудника](docs/model/user-stories/USRSTR-1-request-booking.md), [историю администратора](docs/model/user-stories/USRSTR-2-confirm-booking.md) и ответ на `Q-1` в [указателе](docs/model/INDEX.md). Участники договорились показывать заявку сразу, а бронь подтверждать отдельно.
3. Проследите `USRSTR-2/ACPT-2` от запрета второй брони к [переходу](docs/model/lifecycles/AGGR-1-request.md), [проектному решению](docs/model/slices/booking/design.md), [задаче](docs/model/slices/booking/tasks.md) и [тесту](test_booking.py).

Представьте, что на один слот теперь можно подтверждать две заявки, поскольку у команды появился второй комплект оборудования. Из корня репозитория выполните:

```sh
python3 dev-cycle/scripts/trace.py --model examples/equipment-booking impact USRSTR-2/ACPT-2
```

В выводе будут переход `AGGR-1/TR-2`, метрика `MTR-1`, решение `DES-1`, задачи среза, риск и строка с тестом. Переходу нужно новое условие, тесту — сценарий отказа на третьей заявке. Задача подачи заявки попадает в список через общее проектное решение. По ней достаточно проверить, затрагивает ли изменение интерфейс подачи.

Связи модели показывают область ревью. Решение о правках принимают после разбора найденных связей.
